# Spec：安全的切片库维护预览与显式清理（Issue #476）

> Issue：[Gnosil/semantix#476](https://github.com/Gnosil/semantix/issues/476)
> 状态：已评审并获用户授权实施（2026-09-15）；实现及验收记录见 §9。
> 评估代码：`upstream/main` 的 `2933e1b9`；分支：`codex/issue-476-memory-prune`。
> 判级：Spec-Required，涉及新增 CLI 行为和批量删除的失败语义。
> 流程：必要性评估 → spec 评审 → 决定是否实施 → 实现与验收。

## 1. 必要性判断

**结论：有必要修补安全维护缺口，但不应按“从零补一套记忆维护系统”实施。建议保留 issue，收窄为默认只读的维护入口、保守候选规则、可解释清单和批量执行一致性。**

“没有维护与清理机制”不符合当前代码。已有能力覆盖容量治理、评分淘汰、归档和部分去重，因此不能用“库会无限增长”“没有任何清理方法”作为立项依据。

本次未读取用户真实记忆库，也没有生产库规模、重复率、检索退化或磁盘节省的测量数据。下面的必要性来自可定位的行为缺口，不宣称已有性能收益或紧急的线上容量事故。

### 1.1 已有能力及实际边界

| 能力 | 代码证据 | 对 #476 的含义 |
|---|---|---|
| 正常抽取的完全相同内容复用 ID | [`sliceID` / `dedup`](../../kernel/slice/extractor.go)，ID 已包含类型、scope 和内容；[`Put`](../../kernel/slice/file_store.go) 按 ID 覆盖 | 常规重复抽取不必另建内容哈希或去重索引；异 ID 导入和历史记录才可能留下完全重复项 |
| 年龄、价值、容量淘汰 | [`runGC`](../../cmd/semantix/gc.go)、[`GC`](../../kernel/slice/maintenance.go) | 已有 `--retention-days`、`--min-weight`、`--max-slices`，不能重复建设 |
| 使用与反馈参与价值评分 | [`ComputeWeight`](../../kernel/slice/score.go) 使用 `LastUsed`、Hits、Injected、Rejected 和 UserFeedback | 不需要新的评分器；但低分不等于已确认可以安全删除 |
| 启动时容量治理 | [`gateway.New`](../../gateway/gateway.go) 在加载索引前运行 GC | 已有进程边界维护，不是完全没有自动控制；运行期间增量仍可能超过上限 |
| Context 近似合并 | [`ConsolidateContext`](../../kernel/slice/consolidate.go)；`gc --consolidate-context` | 已覆盖一种近似重复；当前按 token 集合合并并逐项写删，不能当作通用安全去重事务直接复用 |
| 预览及 JSON | `gc --dry-run --json` | 已有骨架，但默认 `gc` 会修改数据，且缺候选类型、来源、创建时间、空间估计及明确的保留关系 |
| 归档及恢复入口 | `GC` 默认由 CLI 指定归档路径；`Export` / `Import` | 用户不必直接操作数据库；导入会重新设置信任来源，Result 会回到 probation，不是无条件恢复验证状态 |
| 失效依赖阻止 L3 复用 | [`L3Decider.verified`](../../kernel/cache/l3.go) | 依赖失效已有使用时防护；“不能复用”与“可以删掉”是不同判断 |

### 1.2 仍然值得解决的具体场景

1. 用户只想查看维护建议却执行裸 `gc`，会触发重评分、容量淘汰和日志折叠。增加使用文档不能使它成为默认只读入口。
2. 创建于 180 天前、今天命中且已验证的 Result，仍会命中 `gc --retention-days 90` 的年龄规则；该规则只读 `CreatedAt`，没有近期使用保护。
3. `gc --dry-run` 在开库时走 `NewFileStore`：不存在的文件会被创建；不匹配的 journal 可能被改名保存。GC 内部不写数据，不代表整条 CLI 路径严格只读。
4. 用户想知道“为什么删、来自哪个会话、重复项保留哪个”，现有 ID 分组报告不够完整。
5. `CompactWith` 在 base 文件替换成功后，还有 `Stat`、删除旧 journal、创建新 journal 等可能失败的操作；已有 rename 失败测试不能证明所有错误都完整回滚。GC 的通用 Store 回退和 Context 合并还包含逐条写删。

这些缺口说明 #476 不适合直接作为重复 issue 关闭。但也不足以支持语义相似度模型、自动后台删除、整库数据库迁移等扩张。

### 1.3 不做的范围

- 不新建评分器、embedding 去重索引、内容哈希、计划哈希、冻结基线或额外发布门禁。
- 不增加定时任务或新的后台删除策略；不修改 gateway 现有容量策略。
- 不删除 `harness/memory` 的用户事实、历史会话、desktop 历史切片或归档文件。本 issue 的对象是 `kernel/slice` 切片库。
- 不因 commit 不同、一次检索失败、低 Weight、权限错误或任意正文里出现不存在路径就删除。
- v1 不做通用语义近似去重，也不把现有 Context 合并直接接到默认删除流程。

## 2. 方案选择

| 方案 | 评估 |
|---|---|
| 只补现有 `gc` 的说明文档 | 能改善发现性，但不能解决默认只读、近期保护及整批失败一致性，不足以完成 issue |
| 把现有 `gc` 默认改成 dry-run，要求 `--apply` | 命令更少，但会改变已有脚本行为；本轮不建议夹带这一兼容性变更 |
| 新增薄入口 `prune`，在现有 slice 包内复用元数据、存储和输出框架 | **建议采用**。新增的是保守清理策略和展示，存储事务能力放回现有 file store，不另建记忆系统 |
| 新建独立清理服务或迁移数据库 | 当前证据不足，不做 |

只有在 §6 的一致性要求能以合理范围实现时，才建议进入代码阶段。若必须进行大规模存储重构，应先拆出存储问题；不能用逐条 Delete 加补偿 Put 冒充事务完成验收。

## 3. CLI 与范围

```sh
semantix prune --scope project
semantix prune --scope project --dry-run --json
semantix prune --scope user --dry-run --older-than-days 180
semantix prune --scope project --apply
semantix prune --scope project --project owner/repo --project-root /workspace/repo --dry-run
```

- 不传 `--apply` 一律只读；`--dry-run` 是显式别名；同时传入二者报参数错误。
- `--scope` 默认 project，仅接受 project/user。选库之后还必须按 `Slice.Scope` 筛选，避免 `--db` 指向混合库时误删其他范围。
- `--db` 显式覆盖选库；否则 project 使用现有配置的项目库，user 使用现有用户库，不误用 project 的 `store.db`。
- `--older-than-days` 默认 90，正整数且受防溢出的范围校验；控制年龄类候选。
- `--recent-days` 默认 30，正整数；近期命中、注入及新切片保护优先于所有删除规则。
- `--project` 可限制 `ProjectSlug`；与 `--project-root` 成对使用时才检查路径。未提供可靠项目映射时，不执行失效路径判定，报告该检查已跳过。
- 非法 scope、冲突参数、无效天数在开库前返回现有 CLI 的 usage 错误码 2。
- 库不存在时报告空计划，连目录和空数据库都不创建。库损坏、journal 不匹配时明确报错，不自动修复或跳过坏行后继续删除。
- `--apply` 对执行时的当前状态重新生成计划；不声称它执行了上次预览保存的 ID 集合。执行结果输出实际提交的候选清单，不引入计划文件或计划哈希。

## 4. 候选规则与保留规则

所有时间判断在一次操作开始时取同一个 `now`。相同数据、参数、文件状态和判定时间应得到相同计划；跨过年龄阈值后允许计划变化。

### 4.1 先判断保护条件

以下切片保留，不因其他规则绕过保护：

- `CreatedAt` 未知、异常或在未来；类型或状态含无法理解的新取值。
- 创建时间或 `Stats.LastUsed` 在近期保护窗口内。
- Hits/Injected 非零但 `LastUsed` 缺失，无法证明长期未用。
- `OriginUserCurated`、正向 UserFeedback 或已有 Useful 信号；不把用户明确保留的知识当一般缓存清理。
- 已验证的 Result。v1 全部保留，比 issue 的“已验证且近期命中”要求更保守，避免缺少验证时间戳时错误推断过期。

非 Result 类型没有通用验证状态，不能把“没有 ResultStatus”解释成长期未验证。

### 4.2 v1 可删除候选

| 原因码 | 条件 | 边界 |
|---|---|---|
| `exact_duplicate` | 相同类型、scope、正文原始字节，且项目、依赖、基准 commit、模型、上下文、信任及验证等影响复用的元数据兼容 | 仅处理异 ID 重复；不跨项目/信任边界合并，不规范化代码空白来制造相等 |
| `missing_dependency` | 项目映射明确，显式 `Meta.Deps` 引用的本地文件被确认不存在 | 不扫描正文；路径穿越、符号链接、不明根目录、权限/IO 错误都不能作为不存在的证据；逐级检查父路径，避免跟随链接越界 |
| `stale_unused` | 已知创建时间超过年龄阈值，且 LastUsed 也超过阈值，或完全没有使用记录 | 有使用计数而无使用时间时保留；新建切片不因零命中被删除 |
| `stale_probation` | Result 明确处于 probation，且满足同样的年龄与未使用条件 | 未知或缺失状态不按本条推定为拒绝 |
| `stale_rejected` | 有 Rejected 或负向反馈证据，且满足同样的年龄与未使用条件 | Rejected 是计数，没有拒绝时间；只报告旧且闲置的切片，不能声称知道“被拒绝多久” |

单条可以有多个原因；原因按固定顺序输出。重复组先选定可保留代表，再排除成员；所有 `retained_id` 必须指向最终仍存在的条目，不能出现 A 指向 B、B 又被年龄规则删除的链条。

代表从独立满足保留条件的成员中选择，按：受保护优先 → 最近使用时间降序 → 创建时间降序 → ID 升序。多个受保护项可以同时保留。如果全组都符合年龄/失效清理条件，则按这些原因清理全组，不生成悬空的保留关系；不能人为留下一个旧代表再在下次运行删除它。去重不修改代表正文、信任、验证或统计字段；因此不引入合并统计及跨来源知识升级。

来源和正文“高度相似”只能证明内容相近，无法证明删除不会丢失关键否定词、版本或适用条件。此项建议从第一版删除范围移出，不把它伪装成已满足的验收项。

## 5. 可解释输出与空间含义

人类可读输出与 `--json` 使用相同计划数据，沿用现有 envelope。候选按 ID 排序，空集合输出数组。

每项包含：`id`、`type`、`scope`、`reasons`、`source_session`、`created_at`、`last_used`、`estimated_reclaimable_bytes`、可空的 `retained_id`。摘要包含扫描/候选/保留/已删除数量，以及未执行的检查及原因。

只输出必要元数据，禁止输出 Content、Embedding、验证证据正文或完整依赖明细。会话标识等外部字符串在文本输出中转义控制字符，必要时脱敏；JSON 使用正常编码，不拼接不可信文本。来源未知明确标为 unknown。

`estimated_reclaimable_bytes` 按候选持久化记录的序列化字节估计，包含已有 raw embedding；不能只把正文长度算作存储大小。它表示活跃记录的逻辑回收量，**不保证文件立即缩小**。base/journal 中的历史记录及默认归档都会影响实际磁盘占用；输出和帮助文档必须明确这一点，不承诺总目录净释放量。

计划和执行报告可由调用者重定向保存供审计。不得为了审计在默认预览期间写日志、备份或额外数据库。

## 6. 存储一致性设计要求

### 6.1 严格只读

新增维护用读取路径，复用现有 base/journal 解析，禁止调用会创建数据库、stash journal 或打开追加句柄的初始化路径。读取和关闭均不改写数据库、journal、归档、mtime 或统计。读取权限不足时保持原状并返回错误。

### 6.2 一批删除只提交一次

实施时应在现有 file store 内提供整批提交能力。计划、校验和删除必须基于受保护的当前状态，不采用 `ListAll` 后逐条 `Delete` 的通用回退。不具备事务能力的其他 Store 明确拒绝 apply。

优先评估单文件原子 journal 替换：保留与 base 对应的既有日志记录，添加完整批次删除记录到同目录临时文件，写入、同步、关闭成功后一次替换 journal。提交前失败删除临时文件，原 base/journal 不变；不要将可失败的 compaction 绑在这一批提交之后，再以它的失败声称删除已回滚。

这只是待验证的实现方案，不是当前代码已提供的保证。实施必须解决以下具体问题：

- **并发写入**：现在的 `sync.Mutex` 只保护单个句柄。另一个进程或旧句柄可能持有待替换的 journal，原子 rename 本身不能防止它丢失后续写入。需要所有相关写入者参与既有存储层的互斥/事务协调，并在维护后重新加载状态；只给 prune 自己加锁不成立。
- **维护窗口**：沿用进程边界维护，运行中的 gateway 内存索引不会自动刷新。apply 必须取得真实的独占维护窗口；活跃写入者存在时明确拒绝，不能仅凭帮助文档假定没有并发。
- **故障边界**：临时文件创建、写入、Sync、Close、替换每一步都要有失败注入测试；验证 Windows 和 Unix 支持的替换语义。崩溃恢复后只能看到整批之前或之后，不能一部分消失。
- **提交后的结果**：成功替换是提交点；stdout 断开属于报告失败，不是事务回滚。错误信息需区分“未执行”与“已提交但报告失败”，禁止返回模糊的失败并让用户误以为数据未改。

这些要求来自“旧 writer 继续向旧 journal 写入”和“多步骤替换中途报错”两种明确的数据丢失场景。优先用普通互斥、文件事务和故障测试解决，不新增哈希、冻结契约或泛化门禁。

### 6.3 保留既有归档 safeguards

默认先将候选完整记录写入受限权限的归档并同步，成功后才提交删除，不增加默认硬删或 `--no-archive` 分支。归档失败则活跃库不变；删除提交失败时可能留下多余备份，但活跃库不得部分删除。

“完整回滚”在本 spec 中指活跃库内容、统计与可检索集合不发生部分改变，不要求已成功写出的恢复副本消失。归档的准确组织方式需在实现前评审确定，并验证 raw embedding 和元数据完整保留。恢复仍遵守现有 Import 信任规则，不绕过 Result 重新验证。

## 7. 实施拆分与验收

按以下顺序推进，每步使用普通单元/集成测试，不引入新基线或测试门禁：

1. 验证现有写入者协调方式以及整批提交方案，明确 Windows/Unix 行为；若范围超出本 issue 可承受的存储修改，先拆题，不先发布缺少一致性的 apply。
2. 增加纯候选计划器及严格只读快照，用确定的时钟和临时库测试规则。
3. 接入薄 CLI、文本/JSON 输出及归档后整批执行。
4. 补充用户文档，解释与 gc 的区别、维护窗口、恢复后的信任状态和空间估计。

验收场景：

- project/user 分库与混合 scope、显式 db 和项目配置选库正确，其他 scope 不变。
- 裸命令与 `--dry-run` 对存在/不存在/损坏/不匹配 journal 的库均无写入副作用。
- 正常抽取相同 ID 不重复计数；异 ID 完全重复项能给出最终保留关系；不同类型、项目、依赖或信任状态不得误合并。
- 明确失效路径进入候选；根目录不明、权限错误、符号链接和越界路径保留；user scope 不拿当前工作目录验证其他项目。
- 旧而长期未用的切片进入候选；已验证且近期使用、创建时间未知、旧计数缺时间戳、用户保留项不进入候选。
- 同一输入和时钟重复计划稳定；apply 成功后再计划不继续删除代表项或其他范围的记录。
- 文本/JSON 都有原因、来源、时间、空间说明和保留关系；正文中的测试 secret 及控制序列不会出现在报告。
- 提交前任意失败重新开库后活跃数据全保留；成功后整批删除；并发或旧句柄不得丢失新增/统计更新；归档可读取并按现有规则恢复。
- 现有检索、验证、抽取、GC、合并和导入回归通过；不能只跑新 prune 测试。

## 8. 本轮验证与待评审结论

本轮只核对现有能力，已执行：

```sh
go test ./kernel/slice ./cmd/semantix -run 'Test(GC|Consolidate|Compact|Import|Export)' -count=1
```

两个包均通过。它证明所选已有维护测试仍通过，不证明新 prune 已实现，也不证明未覆盖的事务故障已经安全。

建议评审决定：**同意缩小后的安全维护工作，暂缓语义近似清理。** 优先确认 §6 的存储协调成本，以及“失败可留下恢复副本、但活跃库必须原状”的回滚范围。若唯一诉求只是控制库大小，已有 gc 足够，无需为这一诉求另做 prune；如果接受 issue 提出的默认只读与安全批量执行要求，则仍有明确的实施价值。

以上为评审时的评估记录。用户随后确认按本 spec 实施，并要求完成后创建 PR。

## 9. 实现记录

- `prune` 为薄 CLI；规则与计划输出位于 `kernel/slice/prune.go`，只读快照、归档和原子提交位于 `prune_store.go`。不改变 GC 的默认策略。
- 普通 `NewFileStore` 句柄从加载之前到 Close 一直持有 `.maintenance.lock` 的共享锁；维护持有独占锁。Unix 使用 flock，Windows 使用 LockFileEx。锁文件不在解锁时删除。库忙时预览/apply 均拒绝，关闭后的句柄不能复活写入；新开句柄重新加载提交后的状态。
- 锁协议要求参与者使用本版本存储 API；旧二进制和任意外部文件编辑器不受 advisory lock 约束，操作文档明确要求先停止这些写入者。未有锁文件的旧库允许纯只读预览，若读取期间出现新锁文件则丢弃不确定快照。
- 归档采用独立的 `<db>.prune-archive-*.jsonl`，创建权限 0600，完整写入、同步和关闭后才提交。每个批次有单独的恢复文件，不与旧 GC 归档追加操作混用。
- apply 保留旧日志的完整记录并追加本批删除记录，同目录临时 journal 写入/同步/关闭后一次替换。不会在提交后调用 compaction，再用后续 IO 错误误报回滚。
- 只读维护严格解析现有字段；损坏、未知字段、未知日志操作、base 与 journal 不匹配均报错，保留原文件。使用已有 journal 代际信息，不新增哈希或落盘格式。
- 新测试覆盖保护规则、重复适用边界、路径映射/符号链接、scope、只读文件及 mtime 不变、完整归档、二次运行、各提交前故障、跨进程排他/进程崩溃释放、关闭句柄不可复写、CLI 文本/JSON 和提交后输出失败。
- 最终验证：Windows 上 `go test ./kernel/... ./cmd/semantix ./gateway/... ./harness/semantix` 与同范围 `go vet` 通过；Linux / Go 1.26.5 上同范围 `go test -race` 与 `go vet` 通过。包含提交点前/后强制退出子进程并重新开库检查整批状态的测试。
- 两处既有测试生命周期修正：CLI 退出码测试隔离本机 PATH 的 agent 安装，bridge 测试在临时目录清理前 Close 并等待异步统计写入。未修改这些功能的生产行为。
